The file has one tracked version, introduced in the initial commit; this history does not establish that an earlier 20-record file existed. Every record is a JSON object with exactly `question`, `ground_truth`, and `contexts`; every question and answer is nonempty, each `contexts` is a one-element text list, and normalized exact question duplicates number zero. There are **zero explicit IDs**, so unique persistent IDs number zero. The audit assigns positional `legacy-001` through `legacy-018` only for tracking this exact file version. These IDs must be replaced with permanent IDs before scoring.

Sanitized real structure (values omitted): `{"question":"<text>","ground_truth":"<generated answer>","contexts":["<generated-input passage>"]}`. `generate_dataset.py:33-51,61-85` uses DeepSeek-R1 via OpenRouter, samples up to 100 chunks at random, adds the input chunk as `contexts`, and skips failed generations. It stores no PDF filename/page or human verification. The current 18 may reflect prior generation history; no evidence establishes why 18 rather than the reported 20 were saved. `ground_truth` and `contexts` are generated candidate material, not certified gold labels. Several candidate answers add reasoning beyond the excerpts, requiring PDF review.

All 18 lack a source paper ID/filename, one-based PDF page, verified supporting passage, trusted reference answer, human verification, question type, answerability label, and split. None is currently eligible for strict document retrieval metrics, passage metrics, answer correctness, or verified abstention. See `phase3-annotation-gaps.csv`.

## Exact 10-record cause and invalid formulas

`evaluator.py:206-214` loads the JSON and unconditionally sets `test_cases = all_cases[:10]`. Thus this revision evaluates at most ten of the **18 present** records. An earlier 20-record file would also have been truncated to ten; its existence on this revision is unverified. The generator's random `min(100, len(chunks))` is unrelated to this ten-record selection.

`evaluator.py:125-198` calls `run_logic_engine`, examines only the returned fact strings, uses `grade_with_llm` for a combined context check and individual facts, then mixes query-level FN with chunk-level TP/FP. `evaluator.py:156-186` adds `TOTAL_DOCS - 1` (or a function of returned fact count) as TN although unreturned papers were never judged. `compute_metrics` then publishes accuracy and F1 from incompatible units and fabricated negatives. Its zero-on-grader-exception behavior also conceals failures. `api.py:195-238` forwards these values and returns fabricated sample metrics when backend modules are absent. README evaluation claims and the analytics UI repeated those metrics. Neither these figures nor old comments in `logic_engine.py` are validated Phase 3 baselines.

## Call path and provider audit

Original path: JSON load → first ten → `run_logic_engine(question)` → `database.search_vault` hybrid retrieval (embedding model + Chroma and optional BM25) → BGE reranking/tri-state grading → `_combined_relevance_check` → optional query rewrite, supplemental search and extraction → final/soft generation → evaluator `ChatGroq` context/fact grading → TN-based report and charts. `logic_engine.call_llm` calls `providers.chat` for all pipeline LLM work, supporting `LLM_PROVIDER=groq|ollama`. The old `evaluator.py:7,16` instead imports/constructs `ChatGroq` directly, bypassing Ollama and potentially requiring a key at import. `generate_dataset.py` separately requires `OPENROUTER_API_KEY`; it is an optional candidate generator.

`.env.example` documents `GROQ_API_KEY`, `LLM_PROVIDER` (default Groq), `OLLAMA_BASE_URL` (default localhost:11434), `OLLAMA_MODEL` (default llama3.1:8b), and optional `OPENROUTER_API_KEY`. `providers.py` checks the Groq key only when Groq is called; local Ollama must be reachable with the requested model. Pure `database.search_vault` calls do not use an LLM, though they require local Chroma/index and embedding model. `logic_engine.run_logic_engine` does use the configured provider. A document ID is a SHA-256 prefix of the filename; child/parent chunk IDs and zero-based `page_index` are index metadata. Gold evidence should use canonical `source_filename`, one-based PDF page, and quote; chunk IDs may change on reindexing. `search_vault` returns expanded parent text and metadata but its fused ranking does not expose a trustworthy per-rank score, so Phase 3 reports rank with null score.

## Minimal corrective path

Validate candidates without rewriting them; require explicit human-verified paper/page/quote labels for eligible binary relevance, and grade only when justified. Replace the evaluator with an LLM-free hybrid retrieval command that processes all valid eligible records by default and records exclusion/failure counts. Delete unsupported TN, accuracy, specificity, and old charts from reporting/API and home-page previews. Preserve retrieval and provider algorithms/configuration. Unit test the validator, metrics, and all-record processing with synthetic results. For this repository snapshot, publish an annotation gap and **no quality baseline**.
